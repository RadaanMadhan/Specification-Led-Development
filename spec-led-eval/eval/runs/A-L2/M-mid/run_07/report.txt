==============================================================================
  Mutation tests  (assertion-strength validation)
==============================================================================

  Strategy: replace each named fact's body with `{}` (no constraint),
  then re-run Alloy. Each listed assertion should now FAIL on the
  mutated model. If it still PASSes, the assertion is vacuous and
  must be strengthened.

  - MUTATE F_AppendOnlyAuditEntries  → runs/A-L2/mutated_F_AppendOnlyAuditEntries.als
    rationale: Clearing F_AppendOnlyAuditEntries removes the constraint that no two events on the same application may share the same (prevStatus, newStatus) pair. Injecting a duplicate transition forces a counterexample that both AppendOnly and FR_019_OneAuditPerTransition must catch.
    expected to FAIL: AppendOnly, FR_018_AuditAppendOnly, FR_019_OneAuditPerTransition
      - AppendOnly: FAIL (expected)
      - FR_018_AuditAppendOnly: FAIL (expected)
      - FR_019_OneAuditPerTransition: FAIL (expected)

  - MUTATE F_DecisionByAssignedOfficer  → runs/A-L2/mutated_F_DecisionByAssignedOfficer.als
    rationale: Clearing F_DecisionByAssignedOfficer allows any loan-officer user to appear as decidedBy on a Decision regardless of the application's assignedOfficer. The injection creates a decision whose decidedBy differs from the application's assignedOfficer, which is exactly what FR-013 prohibits.
    expected to FAIL: FR_013_OnlyAssignedOfficerDecides, OwnershipBasedAccess
      - FR_013_OnlyAssignedOfficerDecides: FAIL (expected)
      - OwnershipBasedAccess: FAIL (expected)

  - MUTATE F_PermissionMatrix  → runs/A-L2/mutated_F_PermissionMatrix.als
    rationale: Clearing F_PermissionMatrix leaves the Allowed relation completely unconstrained. The injection places a compliance reviewer in the DecideApp cell, violating FR-004 and LeastPrivilege — exactly the cells the permission-matrix assertions are meant to guard.
    expected to FAIL: LeastPrivilege, FR_002_CustomerPermissions, FR_004_ComplianceReadOnly, PermissionGrounding
      - LeastPrivilege: FAIL (expected)
      - FR_002_CustomerPermissions: FAIL (expected)
      - FR_004_ComplianceReadOnly: FAIL (expected)
      - PermissionGrounding: FAIL (expected)

  - MUTATE F_OneInFlightPerCustomer  → runs/A-L2/mutated_F_OneInFlightPerCustomer.als
    rationale: Clearing F_OneInFlightPerCustomer removes the structural enforcement of the unique-partial-index on (customer_id) WHERE status IN ('Submitted','Under Review'). The injection forces two distinct applications for the same customer to both be in-flight simultaneously.
    expected to FAIL: FR_008_OneInFlightPerCustomer
      - FR_008_OneInFlightPerCustomer: PASS (vacuous?)

  - MUTATE F_DecidedAppsHaveDecision  → runs/A-L2/mutated_F_DecidedAppsHaveDecision.als
    rationale: Clearing F_DecidedAppsHaveDecision allows an application to reach Approved or Rejected status with no corresponding Decision row, violating the atomicity guarantee (FR-015) that status update and decision insert are inseparable.
    expected to FAIL: FR_015_DecisionExistsForDecidedApps, AuditCompleteness
      - FR_015_DecisionExistsForDecidedApps: PASS (vacuous?)
      - AuditCompleteness: PASS (vacuous?)

  - MUTATE F_ClaimEventExists  → runs/A-L2/mutated_F_ClaimEventExists.als
    rationale: Clearing F_ClaimEventExists allows an application to reach UnderReview, Approved, or Rejected with no Submitted→UnderReview audit entry. The injection creates an Approved application whose audit trail has only the initial submission event, breaking the count-based AuditCompleteness check and FR_011.
    expected to FAIL: FR_011_ClaimAuditEntry, AuditCompleteness, FR_017_AuditPerStatusChange
      - FR_011_ClaimAuditEntry: FAIL (expected)
      - AuditCompleteness: FAIL (expected)
      - FR_017_AuditPerStatusChange: FAIL (expected)
