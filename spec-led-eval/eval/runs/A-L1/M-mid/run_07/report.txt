  Strategy: replace each named fact's body with `{}` (no constraint),
  then re-run Alloy. Each listed assertion should now FAIL on the
  mutated model. If it still PASSes, the assertion is vacuous and
  must be strengthened.

  - MUTATE F_OnePendingPerCustomer  → runs/A-L1/mutated_F_OnePendingPerCustomer.als
    rationale: Removing this fact allows the model to place two PendingReview applications under the same customer. The injection forces exactly that configuration, making FR_005_OnePendingPerCustomer find a counterexample.
    expected to FAIL: FR_005_OnePendingPerCustomer
      - FR_005_OnePendingPerCustomer: FAIL (expected)

  - MUTATE F_PermissionMatrix  → runs/A-L1/mutated_F_PermissionMatrix.als
    rationale: Clearing this fact unpins the permission relation, allowing Alloy to invent a matrix where Customer -> PostDecision is present or BankStaff -> PostApplications is present. The injection adds those forbidden cells, which LeastPrivilege and FR_015 are specifically designed to catch.
    expected to FAIL: LeastPrivilege, PermissionCompleteness, PermissionGrounding, FR_015_StaffOnlyDecisionActions
      - LeastPrivilege: FAIL (expected)
      - PermissionCompleteness: FAIL (expected)
      - PermissionGrounding: FAIL (expected)
      - FR_015_StaffOnlyDecisionActions: FAIL (expected)

  - MUTATE F_AuditCompletenessDecision  → runs/A-L1/mutated_F_AuditCompletenessDecision.als
    rationale: Removing this fact allows a decided (Approved/Rejected) application to exist with no corresponding decision-type audit entry. The injection creates an approved application whose audit trail contains only a Submitted entry, violating AuditCompleteness and FR_016.
    expected to FAIL: AuditCompleteness, FR_016_AuditTrailComplete, AttributionCorrectness, FR_014_NotificationOnDecision
      - AuditCompleteness: FAIL (expected)
      - FR_016_AuditTrailComplete: FAIL (expected)
      - AttributionCorrectness: FAIL (expected)
      - FR_014_NotificationOnDecision: FAIL (expected)

  - MUTATE F_AppendOnly  → runs/A-L1/mutated_F_AppendOnly.als
    rationale: Removing this fact allows two AuditEntry atoms with the same application and the same eventType to coexist, which is what AppendOnly forbids. The injection forces two Submitted entries for the same application.
    expected to FAIL: AppendOnly
      - AppendOnly: PASS (vacuous?)

  - MUTATE F_OwnershipBasedAccess  → runs/A-L1/mutated_F_OwnershipBasedAccess.als
    rationale: Clearing this fact lets the model construct an Operation where a Customer fetches an application owned by a different Customer, which is exactly the information-leakage scenario SC-004 prohibits. The injection forces such an operation to exist.
    expected to FAIL: OwnershipBasedAccess, NoInformationLeakage, FR_013_CustomerIsolation
      - OwnershipBasedAccess: FAIL (expected)
      - NoInformationLeakage: FAIL (expected)
      - FR_013_CustomerIsolation: FAIL (expected)

  - MUTATE F_DecisionStatusConsistency  → runs/A-L1/mutated_F_DecisionStatusConsistency.als
    rationale: Removing this fact breaks the invariant that a decided application has exactly one decision with matching type. The injection installs an Approved application with no decision at all, causing FR_010 and FR_011 to find counterexamples.
