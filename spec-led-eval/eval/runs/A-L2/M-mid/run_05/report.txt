  Mutation tests  (assertion-strength validation)
==============================================================================

  Strategy: replace each named fact's body with `{}` (no constraint),
  then re-run Alloy. Each listed assertion should now FAIL on the
  mutated model. If it still PASSes, the assertion is vacuous and
  must be strengthened.

  - MUTATE F_AppendOnlyAuditEntries  → runs/A-L2/mutated_F_AppendOnlyAuditEntries.als
    rationale: Removing this fact allows duplicate audit entries for the same (application, prevStatus, newStatus) triple. The AppendOnly and FR_018_AuditAppendOnly assertions both require no two entries on the same application to share the same (prev, new) pair, so they find counterexamples once the uniqueness constraint is lifted.
    expected to FAIL: AppendOnly, FR_018_AuditAppendOnly, FR_019_ExactlyOneEntryPerTransition
      - AppendOnly: FAIL (expected)
      - FR_018_AuditAppendOnly: FAIL (expected)
      - FR_019_ExactlyOneEntryPerTransition: FAIL (expected)

  - MUTATE F_DecisionByAssignedOfficer  → runs/A-L2/mutated_F_DecisionByAssignedOfficer.als
    rationale: Removing this fact allows a Decision to be recorded by any loan officer, not just the one assigned to the application. The FR_013_OnlyAssignedOfficerDecides assertion checks that d.decidedBy = d.forApp.assignedOfficer for all decisions, so it fails when a non-assigned officer's decision is injected.
    expected to FAIL: FR_013_OnlyAssignedOfficerDecides, AttributionCorrectness
      - FR_013_OnlyAssignedOfficerDecides: FAIL (expected)
      - AttributionCorrectness: PASS (vacuous?)

  - MUTATE F_OneInflightPerCustomer  → runs/A-L2/mutated_F_OneInflightPerCustomer.als
    rationale: Removing this fact allows a single customer to have two simultaneously in-flight (Submitted or UnderReview) applications. The FR_008_OneInflightPerCustomer assertion directly checks that no such pair exists, so it fails when the pair is injected.
    expected to FAIL: FR_008_OneInflightPerCustomer
      - FR_008_OneInflightPerCustomer: FAIL (expected)

  - MUTATE F_OperationsAreAuthorised  → runs/A-L2/mutated_F_OperationsAreAuthorised.als
    rationale: Removing this fact allows operations whose caller's role is not in the permitted set for that operation kind. The LeastPrivilege assertion checks that every operation is covered by an allowed cell; a counterexample is forced by injecting a ComplianceReviewer calling PostClaim.
    expected to FAIL: LeastPrivilege, FR_002_CustomerActions, FR_004_ComplianceReadOnly, FR_023_ComplianceNoWrite
      - LeastPrivilege: PASS (vacuous?)
      - FR_002_CustomerActions: PASS (vacuous?)
      - FR_004_ComplianceReadOnly: PASS (vacuous?)
      - FR_023_ComplianceNoWrite: PASS (vacuous?)

  - MUTATE F_AuditHasDecisionEntry  → runs/A-L2/mutated_F_AuditHasDecisionEntry.als
    rationale: Removing this fact allows a decided application to exist without its corresponding UnderReview→Approved/Rejected audit entry. The AuditCompleteness and FR_015_DecisionAtomicWithAudit assertions both require this entry to exist; they find counterexamples when an Approved application has no such audit entry.
    expected to FAIL: AuditCompleteness, FR_015_DecisionAtomicWithAudit, FR_017_EveryTransitionHasAuditEntry
      - AuditCompleteness: FAIL (expected)
      - FR_015_DecisionAtomicWithAudit: FAIL (expected)
      - FR_017_EveryTransitionHasAuditEntry: FAIL (expected)

  - MUTATE F_ComplianceReadOnly  → runs/A-L2/mutated_F_ComplianceReadOnly.als
    rationale: Removing this fact allows a ComplianceReviewer-role user to appear as the caller of a PostDecision operation. The FR_004_ComplianceReadOnly and FR_023_ComplianceNoWrite assertions both forbid this; they detect the counterexample immediately.
    expected to FAIL: FR_004_ComplianceReadOnly, FR_023_ComplianceNoWrite, LeastPrivilege
      - FR_004_ComplianceReadOnly: PASS (vacuous?)
      - FR_023_ComplianceNoWrite: PASS (vacuous?)
      - LeastPrivilege: PASS (vacuous?)
