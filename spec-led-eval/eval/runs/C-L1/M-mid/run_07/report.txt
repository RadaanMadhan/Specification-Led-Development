  - MUTATE F_AppendOnlyAuditEntries  → runs/C-L1/mutated_F_AppendOnlyAuditEntries.als
    rationale: Clearing this fact removes the constraint that distinct operations must own distinct AuditEntry atoms. The injection then forces two operations to share one entry, which is the structural equivalent of an in-place mutation/overwrite — exactly what AppendOnly and FR_010_AuditImmutable forbid. AuditCompleteness also breaks because the one-to-one invariant no longer holds.
    expected to FAIL: AppendOnly, FR_010_AuditImmutable, AuditCompleteness
      - AppendOnly: PASS (vacuous?)
      - FR_010_AuditImmutable: PASS (vacuous?)
      - AuditCompleteness: PASS (vacuous?)

  - MUTATE F_CareTeamGating  → runs/C-L1/mutated_F_CareTeamGating.als
    rationale: Clearing this fact removes the rule that Permitted outcomes require an active CareTeamMembership. The injection forces a Permitted operation whose caller has no active membership for the target patient, directly violating the care-team-only access rule (FR-006, SC-010).
    expected to FAIL: OwnershipBasedAccess, FR_006_CareTeamGating
      - OwnershipBasedAccess: FAIL (expected)
      - FR_006_CareTeamGating: FAIL (expected)

  - MUTATE F_NoInformationLeakageFact  → runs/C-L1/mutated_F_NoInformationLeakageFact.als
    rationale: Clearing this fact removes the byte-equivalence rule between Denied and NotFoundOrDenied responses. The injection forces a Denied operation to return OkResponse (distinct from NotFoundResponse), making the two branches distinguishable to an external observer — exactly the information leak FR-007 and SC-003 forbid.
    expected to FAIL: NoInformationLeakage, FR_007_ByteEquivalentDenyNotFound
      - NoInformationLeakage: FAIL (expected)
      - FR_007_ByteEquivalentDenyNotFound: FAIL (expected)

  - MUTATE F_AuditOneToOne  → runs/C-L1/mutated_F_AuditOneToOne.als
    rationale: Clearing this fact removes the requirement that every AuditEntry is owned by exactly one Operation. The injection introduces an orphan AuditEntry not attached to any operation, violating SC-002 ('zero occurrences where an audit entry exists without a matching attempted access') and breaking the always-on audit guarantee of FR-008.
    expected to FAIL: AuditCompleteness, FR_008_AlwaysAudit
      - AuditCompleteness: FAIL (expected)
      - FR_008_AlwaysAudit: FAIL (expected)

  - MUTATE F_PermissionMatrix  → runs/C-L1/mutated_F_PermissionMatrix.als
    rationale: Clearing this fact empties the Allowed relation (or allows any assignment). The injection grants AuditOfficer access to RecordsLookup, which directly violates LeastPrivilege (AuditOfficer must not use the clinical endpoint), PermissionCompleteness (the matrix no longer matches the specified cells), and FR_011_AuditOfficerOnly.
    expected to FAIL: LeastPrivilege, PermissionCompleteness, FR_011_AuditOfficerOnly
      - LeastPrivilege: PASS (vacuous?)
      - PermissionCompleteness: FAIL (expected)
      - FR_011_AuditOfficerOnly: FAIL (expected)

  - MUTATE F_AuditRoleSnapshotCorrect  → runs/C-L1/mutated_F_AuditRoleSnapshotCorrect.als
    rationale: Clearing this fact removes the requirement that the role snapshot in an AuditEntry matches the caller's actual role at the time of the operation. The injection forces a mismatch — an audit entry records a different role than the caller held — which is precisely the misattribution scenario FR-009 (snapshot semantics) and AttributionCorrectness guard against.
    expected to FAIL: AttributionCorrectness, FR_009_AuditEntryShape
      - AttributionCorrectness: FAIL (expected)
      - FR_009_AuditEntryShape: PASS (vacuous?)
