  - MUTATE F_NoSelfApproval  → runs/A-L3/mutated_F_NoSelfApproval.als
    rationale: Removing F_NoSelfApproval allows the model to construct an AuditEntry whose entryActor equals the application's appApplicant on a non-initial transition, directly violating the no-self-approval invariant. The injected fact forces exactly such a counterexample to exist.
    expected to FAIL: NoSelfMutation, FR_013_NoSelfApproval
      - NoSelfMutation: PASS (vacuous?)
      - FR_013_NoSelfApproval: PASS (vacuous?)

  - MUTATE F_PermissionMatrix  → runs/A-L3/mutated_F_PermissionMatrix.als
    rationale: Clearing F_PermissionMatrix allows PermMatrix.Allowed to take any value, so a pure-officer user could appear to have unconditional POST permission and an auditor could have PATCH permission, breaking LeastPrivilege. The injection forces an officer→OpPost cell into PermMatrix.Allowed, which is exactly the cell that must be absent.
    expected to FAIL: LeastPrivilege, PermissionCompleteness, FR_005_AuditorReadOnly, FR_004_OfficerPermissions
      - LeastPrivilege: PASS (vacuous?)
      - PermissionCompleteness: PASS (vacuous?)
      - FR_005_AuditorReadOnly: PASS (vacuous?)
      - FR_004_OfficerPermissions: PASS (vacuous?)

  - MUTATE F_OneInFlightPerApplicant  → runs/A-L3/mutated_F_OneInFlightPerApplicant.als
    rationale: Removing F_OneInFlightPerApplicant allows two LoanApplication atoms to share the same appApplicant while both are in Pending or UnderReview status. The injection creates exactly that scenario.
    expected to FAIL: FR_008_OneInFlightPerApplicant

  - MUTATE F_UniqueInitialAuditEntry  → runs/A-L3/mutated_F_UniqueInitialAuditEntry.als
    rationale: Removing F_UniqueInitialAuditEntry allows either zero or two initial (none→pending) audit entries for a single application. The injection forces two distinct AuditEntry atoms to both be initial entries for the same application, violating uniqueness and the append-only deduplication invariant.

      - AuditCompleteness: PASS (vacuous?)
