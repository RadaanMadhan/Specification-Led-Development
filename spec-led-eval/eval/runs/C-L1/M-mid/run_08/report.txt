  Mutation tests  (assertion-strength validation)
==============================================================================

  Strategy: replace each named fact's body with `{}` (no constraint),
  then re-run Alloy. Each listed assertion should now FAIL on the
  mutated model. If it still PASSes, the assertion is vacuous and
  must be strengthened.

  - MUTATE F_AppendOnlyAuditEntries  → runs/C-L1/mutated_F_AppendOnlyAuditEntries.als
    rationale: Clearing this fact removes the constraint that no two AuditEntries share the same operation. The injection forces two distinct AuditEntries to reference the same AccessOperation, which is a direct model of an audit-log mutation (an entry being 'overwritten'). Both AppendOnly and FR_010_AuditImmutability check this injectivity and will find a counterexample.
    expected to FAIL: AppendOnly, FR_010_AuditImmutability
      - AppendOnly: PASS (vacuous?)
      - FR_010_AuditImmutability: PASS (vacuous?)

  - MUTATE F_AuditCompleteness  → runs/C-L1/mutated_F_AuditCompleteness.als
    rationale: Clearing this fact removes the requirement that every RecordsLookup AccessOperation has exactly one AuditEntry. The injection forces a RecordsLookup operation to exist that has no corresponding AuditEntry atom pointing to it, directly violating SC-001 and SC-002.
    expected to FAIL: AuditCompleteness, FR_008_AlwaysOnAudit
      - AuditCompleteness: FAIL (expected)
      - FR_008_AlwaysOnAudit: FAIL (expected)

  - MUTATE F_PermissionMatrix  → runs/C-L1/mutated_F_PermissionMatrix.als
    rationale: Clearing the permission matrix fact allows Alloy to populate PermMatrix.Allowed arbitrarily. The injection grants a clinical role access to AuditSearch, which is the most dangerous cross-role escalation (a Doctor reading the IG audit log). LeastPrivilege and FR_011_AuditReadableByIGOnly both depend on the matrix being exactly as specified.
    expected to FAIL: LeastPrivilege, FR_011_AuditReadableByIGOnly, PermissionCompleteness, SC_011_AuditEndpointHidden
      - LeastPrivilege: FAIL (expected)
      - FR_011_AuditReadableByIGOnly: FAIL (expected)
      - PermissionCompleteness: FAIL (expected)
      - SC_011_AuditEndpointHidden: PASS (vacuous?)

  - MUTATE F_ByteEquivalentResponse  → runs/C-L1/mutated_F_ByteEquivalentResponse.als
    rationale: Clearing this fact lets Alloy assign any ExternalResponse to any operation outcome. The injection creates a Denied operation that returns RecordResponse instead of NotFoundResponse, directly violating SC-003's byte-equivalence requirement and leaking the existence of a patient to a non-care-team clinician.
    expected to FAIL: NoInformationLeakage, FR_007_ByteEquivalentDenied
      - NoInformationLeakage: FAIL (expected)
      - FR_007_ByteEquivalentDenied: FAIL (expected)

  - MUTATE F_CareTeamMembershipGate  → runs/C-L1/mutated_F_CareTeamMembershipGate.als
    rationale: Clearing the care-team gate fact removes the iff constraint between Permitted outcome and active membership. The injection creates a Permitted RecordsLookup operation for a clinician-patient pair that has no active CareTeamMembership row, directly modelling break-glass access that v1 explicitly prohibits (SC-010).
    expected to FAIL: OwnershipBasedAccess, FR_006_CareTeamMembershipGating, FR_006_NoBreakGlass
      - OwnershipBasedAccess: FAIL (expected)
      - FR_006_CareTeamMembershipGating: FAIL (expected)
      - FR_006_NoBreakGlass: FAIL (expected)

  - MUTATE F_AuditEntryAttribution  → runs/C-L1/mutated_F_AuditEntryAttribution.als
    rationale: Clearing this fact lets AuditEntry fields diverge from the AccessOperation they record. The injection creates an AuditEntry whose clinician field differs from the caller of its linked operation, modelling a misattribution bug (wrong clinician on an audit record) that violates FR-009 and the snapshot-correctness requirement.
    expected to FAIL: AttributionCorrectness, FR_009_AuditEntryFields
      - AttributionCorrectness: FAIL (expected)
      - FR_009_AuditEntryFields: FAIL (expected)
